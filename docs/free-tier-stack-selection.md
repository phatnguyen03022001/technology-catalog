## 1. Verdict and assumptions

**Default for a real product: Cloud Run for ordinary Next.js/Node and Go containers, Neon PostgreSQL, Better Auth in the existing Next.js app, Cloudflare R2 for audio/images, GitHub Actions for CI and repository-bound Python content builds, Resend only when verification/recovery email is required.** Use Cloud Run Jobs for actual application processing, not Actions as an online worker. Begin on recurring free allowances, but accept a small PAYG network bill. Plan around a $0–5 operating target, not a contractual cap. Upgrade one bottleneck at a time.

**Refined default: architecture D, browser + Mac + cloud hybrid (§13).** Keep that cloud topology; perform safe session-local feedback/media work in the browser and prepare editorial assets with existing Mac tools, then independently validate in repository CI. The Mac is not on the learner request path. This can avoid unnecessary work, but does not establish a lower measured invoice than TASK 04: direct R2 media and no mandatory live Python service were already selected.

**Best strict-free Next.js candidate is Netlify Free**, not Vercel Hobby. Netlify wins compatibility and no-bill behavior for a small SSR app; its credit pool is a serious ceiling. **Cloud Run wins integrated runtime hosting** because it keeps the ordinary Node/Go/Python toolchains and removes a hosting vendor. This trades free CDN delivery for metered network traffic and additional cache/build responsibility. No fully evidenced, hard-capped, production-ready $0 stack is established for the English reference workload.

| Workload | Planning assumptions | What is not established |
|---|---|---|
| A: lightweight MVP | Next.js with SSR capability; Go HTTP/JSON; one PostgreSQL database; one identity system; static audio/images; GitHub CI; no worker required | Requests, SSR CPU, DB active time, payload sizes, availability/recovery objectives |
| B: three runtimes | A plus bounded Python content processing; actual asynchronous application jobs only if required | Job duration/frequency, native dependencies, retries and scheduling SLA |
| C: English reference | About 1,000 users and 50–100 peak concurrent learners; Vietnam-first, online-only; learner history; no model training | MAU vs DAU, monthly sessions, read/write amplification, p95 latency, recovery performance |

Concurrency is not a monthly consumption measurement. No statement here proves these plans can serve C. Initial placement proposal is Singapore for app and database, with R2 APAC placement hint for public media. Same city across GCP and AWS is still cross-provider networking; R2 hints are not jurisdiction guarantees. No Vietnam-only residency requirement was supplied.

## 8. Monthly cost model and boundaries

USD planning calculations, no signup credits. Infrastructure invoice excludes separately identified domain acquisition, taxes, operator labor, external LLM/TTS API charges and devices; these remain real TCO drivers, not assumed zero. A–C have no supplied measurements, so no fabricated all-in monthly total is published.

`TCO = subscriptions once per owner + aggregate post-allowance usage + compute/registry/build/network/logs + backup/restore + operator time + taxes.`

| Budget band | What can be supported by evidence | Limit |
|---|---|---|
| $0 | Stack A or B editorial-only can target the included allowances; Netlify/Neon free services stop at quota | No complete production $0 invoice demonstrated. Cloud Run/R2 are bill-enabled. A new domain, transfer or registry growth can break zero immediately |
| $0–5 | C with light, measured usage is the preferred operating target; a small Neon paid workload may fit | This is an allocation target, not an estimate or guaranteed cap. GCP internet transfer and other meters must fit the remaining budget |
| $5–20 | C with intermittent paid DB compute and additional media/job usage is plausible under a measured budget | Does not buy verified HA, 24/7 workers, unlimited email or app-owned auth operations. Persistent DB activity can consume almost the full band |

Worked calculations use the rates in the provider SSOT, **not measured product usage**:

- Netlify MVP planning example: 4 production deploys, 3 GB web transfer, 100,000 web requests and 1 GB-hour compute consume **150 credits**. The remaining pool is not separately available per meter. A second example with 4 deploys, 12 GB transfer and the same requests/compute consumes **330 credits**, beyond Free. Media must bypass Netlify; static JS/HTML and previews still have traffic consequences. These are hypothetical monthly inputs, not estimates for 1,000 learners.
- Neon Free: a fixed 0.25-CU database active 10 hours/day for a 30-day month consumes **75 CU-hours**; active 24 hours/day consumes **180 CU-hours**, which cannot fit the Free compute allowance. Cold-start/autosuspend and other branches also count; do not shard a single workload across free projects to bypass limits.
- Neon Launch: with one 1-GB database, 0.25 CU active for 100 hours costs **$3.00** for compute + database storage; 300 active hours costs **$8.30**. At 730 active hours the same subtotal is **$19.695**. Free compute is not subtracted after upgrading. These subtotals omit retained history, snapshots, other branches, network overage, tax and app hosting.
- R2 Standard: a 20-GB-month library, with operations still within included allowance, has a derived storage subtotal of **$0.15/month**. Backups occupy storage too. Read-heavy delivery can still cost operations money; no egress charge does not cap the invoice.
- Cloud Run: compare aggregate CPU time, GiB-seconds and requests across Next, Go and applicable jobs under one billing account. Free grants are spending discounts with documented reference-region rates; don't add a fresh grant for each project/service or sum billing modes into a larger allowance. No all-in Singapore price is inferred from an Iowa table or a user count.

**Hard boundaries:** Netlify Free pauses at its shared credit limit; Neon Free suspends compute at usage limits and restricts storage growth; Resend has daily as well as monthly limits; GitHub private credit is owner-shared with eligible sandbox compute and storage is separate. **Not exact invoice caps:** Cloud Run max instances, CPU limits, alert budgets, delayed spend caps and Neon approximate consumption quotas. R2 storage/operation PAYG remains a material cost-safety UNKNOWN until account controls and attack traffic are tested.

GCP now documents project/service **spend caps for Cloud Run**. It would be outdated to claim that Google has only alert budgets. It is equally wrong to call those caps exact: they use gross estimated spend before discounts, allow in-flight/delayed overage and do not cover unrelated registry, logging, scheduler, network SKUs or fixed storage. Confirm actual meter attribution; a low gross cap can pause a service even when net charges would have been covered by free credits. An alerts-only budget still never stops usage by itself.

## 9. Integrated security, reliability and exit

- Keep public immutable audio/images on R2/CDN, not streamed through Go/Next. Use cache headers, immutable object keys and checksums. Private/premium media needs authorization: Go-issued presigned S3 URLs provide expiring origin access; custom-domain edge authorization requires a separately evaluated design and can add Worker costs. This study assumes ordinary public static lesson assets, not DRM.
- Keep app and PostgreSQL near each other. Use TLS and bounded pools; pooled transaction semantics do not support every session-level feature. Use direct connections for compatible admin/migration/pg_dump tasks. Do not configure the pool for the host's theoretical maximum concurrency; total app instances × pool size must fit the database's actual capacity.
- Use one auth issuer. Store secure HttpOnly/SameSite cookies appropriately, validate CSRF/origin on mutations, rate-limit recovery/signup and avoid tokens in logs. Use separate least-privilege SQL roles and restore/admin credentials. Go owns business authorization; authenticated does not mean authorized.
- Pin and scan build inputs, deploy immutable images/artifacts, keep the prior known-good revision and use expand/contract DB migrations. A frontend rollback does not undo a destructive schema migration. Coordinate auth schema, JWT keys and asset versions across releases.
- Native logs/metrics are sufficient initially: structured request ID, error class, duration, job status and quota alerts. Configure sampling/retention; do not introduce Sentry, Grafana, Redis, Kafka, Kubernetes, a VPS or IaC just to complete a checklist.
- Recovery planning assumption: daily logical database export plus immutable media/source manifests and an independent encrypted copy, with an initial target RPO ≤24 hours and RTO ≤4 hours. **NOT VERIFIED**; no restore performed. Store database exports outside Neon, e.g. R2, and keep a second encrypted copy outside the Cloudflare account/available authorized environment. An R2 copy alone is not protection from a Cloudflare-wide outage. Scheduler/export compute and retained copies count toward cost.
- Back up auth tables, encryption/signing material through an appropriate secure process, object inventory and media binaries; pg_dump does not back up object storage. Do not assume provider restore history replaces independent backups. Test a restore into isolated PostgreSQL, verify ownership and login, compare object checksums, then rehearse app image rollback. If this cannot meet required learner-data recovery, pay for stronger backup/recovery or block release.
- Exit Cloud Run by running the same OCI images elsewhere; exit Neon via standard PostgreSQL dump/restore; exit R2 using its S3-compatible API/rclone-style tooling; exit Better Auth with its own DB and versioned migrations. Auth replacement still needs session/password-hash compatibility, possible password reset and user-ID mapping. Preserve app-owned learner IDs so provider identifiers are not the sole business key.

### 13.1 Browser-versus-server allocation

Every browser value, including a hash, timer, worker result or Wasm output, is attacker-controlled. **No operation below requires a provider secret in delivered JS/Wasm.** Secret-bearing or authoritative variants stay on the server. A worker improves responsiveness, not trust. Once an answer key or protected asset is delivered, the learner can inspect/copy it; obfuscation is not protection. Browser execution means processing during an active session, not offline learning, durable local learner state or a service worker architecture.

| Operation / classification | Correctness, secrets, manipulation and server verification | Content/privacy boundary | Device, mobile/accessibility and simpler fallback | Concrete cloud meter affected |
|---|---|---|---|---|
| Input normalization, local sorting/filtering, small JSON transformations — **BROWSER_PREFERRED** | Plain JS is sufficient for small data. Version Unicode/case/punctuation rules; Go recomputes canonical answers from bounded original inputs for official submissions | Deliver only authorized fields. Do not ship private datasets/keys just to enable local comparison | Low cost for bounded inputs; keep IME/Vietnamese input intact. Keyboard and textual errors; no worker for a few strings | Removes per-keystroke requests and preview CPU if otherwise sent; final evaluation/write remains |
| Deterministic formative feedback — **HYBRID** | Browser can compare correctly but can forge score or completion. Protected keys remain server-side; assisted feedback must not become independent evidence | Short JS tasks work on common mobile engines; accessible feedback/status. | Microphone recording and self-listening — **BROWSER_PREFERRED** | MediaRecorder captures supported formats; not proof of speaker, duration or independent performance. **Representative browser boundary:** recent Safari on iPhone, Chrome on Android and Firefox on Android are required test targets, not devices tested in this study. If an actual heavy operation appears, compare download/compile/device cost with doing it once editorially before adding a library. ### 13.2 Direct media transfer without weakening authority

For public, licensed teaching media, use immutable versioned objects through the existing R2 production custom domain and normal CDN caching; no application container should relay every audio byte. Premium/private material requires actual access control, not an obscure public URL. R2 presigned S3 URLs use the S3 endpoint rather than the public custom-domain CDN; do not assign public-cache behavior to private delivery.

For an upload that is genuinely needed: Go checks identity, ownership, purpose and allowed size/type, assigns an unpredictable server-owned object key, creates a pending record and signs a short-lived specific operation. Browser transfers directly to R2 using tightly scoped CORS. Server verifies existence/size and, where required, actual decoded format, content safety and checksum before committing metadata; stale or rejected pending objects need cleanup. A signed Content-Type does not establish actual file contents. A client hash or multipart ETag is not a universal trusted content digest. Decode/check work can still require downloading bytes and metered processing. Do not claim that an ordinary presigned PUT enforces an independently verified application size limit; check the selected API and implement real admission/cleanup controls before enabling untrusted uploads.

A presigned URL can be reused until expiry, and CORS controls browsers rather than authenticating arbitrary HTTP clients. Redact URL query credentials from logs/referrers; use short expiry and narrowly allowed operations. An expired URL may surface as a CORS failure, so reacquire authorization rather than endlessly retrying. Revoking an account does not promise immediate revocation of every already-issued URL. R2 operation abuse and orphan storage remain billable risks. Do not introduce this upload subsystem at all when self-review can keep the recording in the browser.

### 14.2. Cache correctness and cost allocation

HTTP caching is not offline application functionality. A fresh browser hit can avoid the network entirely; a CDN hit can avoid the origin; an ETag/304 normally avoids the response body but may still execute authorization, application and database work. `no-cache` permits storage but requires validation; `no-store` forbids new storage and does not retroactively erase old copies. `private` excludes shared caches. Browser history restoration is a separate concern: logout/account switching must clear user-scoped UI/query state and revalidate authority-sensitive actions.

**No arbitrary TTL is selected.** Product freshness, privacy, rights withdrawal and acceptable stale exposure determine the maximum age; absent that policy, mutable/authority-sensitive responses revalidate or bypass storage. Content versioning solves change visibility, not the legal right to retain a downloaded copy.

| Data | Placement / cache key | Freshness and invalidation | Failure behavior / prohibited sharing |
|---|---|---|---|
| Versioned public lessons | Browser/CDN only if the published lesson and included answers are intended to be public; revision/hash + language + representation | Immutable revision URL only where rights permit retention; current publication manifest revalidates; new content gets new revision | Origin fallback; never expose hidden assessment keys through public lesson bundles |
| Public audio/images | R2 custom domain → CDN → browser; content-addressed object | Retention policy controls max-age; withdrawal blocks new origin access and purges relevant CDN objects | Previously cached/downloaded bytes cannot be recalled. Private/withdrawable content may require shorter freshness or authenticated delivery |
| Public catalog metadata | ETag/conditional GET first; local/shared cache only with evidence | Revision/schema/language and all meaningful query parameters in key; explicit publication invalidation | DB/origin fallback with bounded concurrency; do not combine personalized and public variants |
| Learner progress | PostgreSQL authority; account-scoped client presentation | Invalidate/refetch after committed writes; clear on identity change; use row/version conflict handling | No shared HTTP cache. Conservative default `private, no-store`; stale UI never proves a write succeeded |
| Authentication/session | Existing Better Auth verification boundary and authoritative session configuration | Respect actual revocation/session policy; do not add independent Redis sessions | Login/session responses bypass shared cache. Cache outage must not become an authentication bypass |

| Rate counters | Local for best-effort traffic shaping; shared atomic DB or conditional Redis for specified scope | Window and retention follow abuse/allowance policy, not a generic cache TTL | Reset/eviction/failover must not grant unlimited paid operations; shared IP is not learner identity |
| Queue/job state | Durable PostgreSQL operation/status; queue holds dispatch information | Unique operation ID, attempt budget, deadline and recoverable terminal state | Never evict as cache. Queue expiry is not successful completion |
| Runtime configuration | Deployment config by default; cache only explicitly public/tenant-scoped settings | Version and change/revocation propagation contract | No secret caching in public responses; safety-critical missing config denies the affected action |

**Cloudflare boundaries.** Standard CDN behavior does not cache HTML/JSON by default. Do not enable broad cache-everything behavior on authenticated API/RSC/session routes. Preserve origin cache headers, `Vary`, content encoding and framework representation headers; do not strip `Set-Cookie` to make private content cacheable. Public keys must not silently ignore query parameters that change content. Free Cache Rules have a bounded rules allowance (see official evidence); use the existing media domain rather than adding a Worker for basic caching.

R2 public production delivery uses a custom domain; `r2.dev` is a development surface. R2's egress policy does not erase storage/operation charges. Origin misses and cache-fill requests still count against origin meters. Workers Cache API is **local to a data center**, including local deletion, and does not use Tiered Cache; it is not a distributed Redis replacement. Prefer normal `fetch`/CDN caching where that solves the need. Request collapsing at one edge location is not a global stampede lock. Origin shielding/Tiered Cache eligibility and any paid features must be checked before assuming they are included.

**Next.js version boundary.** Official documentation currently identifies v16.4.5; the future application's exact version/configuration is not supplied. The guide now separates caching with and without Cache Components. In the non-Cache-Components model, server `fetch` is not cached by default; choose cache/revalidation behavior explicitly. In the Cache Components model, use the version's opt-in configuration and `'use cache'` semantics. React `cache()` request memoization is not a cross-request distributed cache. Do not paste older Next.js default-fetch assumptions into a new application.

On Cloud Run, local memory/disk cache is per instance and disposable. Built-in caching is enough for single-instance performance-only data or revisioned resources; cache loss may cause extra origin reads, not lost business state. Multiple instances **do not automatically require Redis**. Dynamic rendering or immutable revision URLs may be simpler than coordinating mutable ISR. If cross-instance invalidation is a real requirement, shared bytes alone are insufficient: tags, invalidation state, atomic writes and the pinned handler contract must be coordinated and tested.

Next's **`cacheHandler` (singular)** handles server cache/ISR and related operations; **`cacheHandlers` (plural)** handles `'use cache'`. These are not interchangeable configuration names. `revalidateTag(tag, 'max')` uses stale-while-revalidate; the old one-argument form is deprecated. `updateTag` provides immediate read-your-writes in **Server Actions**, not arbitrary Go callbacks. A Go publication event must reach a separately authenticated, version-appropriate invalidation path if one exists. Rollout also needs consistent builds, Server Actions keys and deployment/version-skew handling; Redis does not solve those contracts. Do not add custom handlers before the application proves it needs them.

**Go progression.** First remove unnecessary reads, fix indexes/query plans, bound queries/pagination and avoid repeated authorization work within one request. If necessary, introduce a size-bounded per-process cache for public rebuildable values, with freshness derived from policy, explicit eviction and per-key request coalescing. Account for memory alongside Cloud Run concurrency. Negative caching must distinguish public absence from unauthorized access; do not cache account-specific 404s globally. Invalidation follows a committed revision, not an optimistic write. Use bounded origin fallback and backpressure so cache failure does not stampede Neon. A shared cache is justified only if measured repeated work, cost or replica inconsistency remains material after these steps.

### 14.5. Minimum correct reliability contract

1. **Authorize and reserve before enqueue.** The backend derives account/tenant identity, validates inputs and checks entitlement. Atomically create the operation/outbox with the business transaction and any expensive-operation allowance reservation. Use a stable operation ID and uniqueness scope; a client's random idempotency key alone cannot bypass quotas. Bind reuse to the same account, operation type and input digest; reject conflicting reuse.
2. **Recover the enqueue gap.** Submit only after commit. A crash between commit and enqueue, or between provider acceptance and recording dispatch, is expected. A bounded dispatcher/reconciler retries unsent operations. Provider task-name deduplication helps but does not replace durable records. If dispatch reconciliation has a timeliness requirement, explicitly fund/operate a scheduler; do not claim it happens magically without a running trigger.
3. **Keep messages small.** Submit operation ID, schema version and references/digests, not secrets, learner recordings, large media or privileged answer keys. The consumer retrieves authorized data from the correct account and rechecks revocation where needed. A signed URL must remain usable for the actual delay/retry window or be regenerated by the authorized consumer.
4. **Claim briefly; do work outside the transaction.** Claim eligible rows with a short transaction; `SKIP LOCKED` is suitable for queue-like access, not general consistent reads. Store lease owner/expiry and attempt version. Commit before network/CPU work. If a lease is used, reject stale-owner finalization with a version/fencing check; add heartbeats only when job duration needs them.
5. **Make effects idempotent.** Unique business constraints and a transaction commit effect + completion together when both are in PostgreSQL. For external email/AI/payment-like calls, use supported provider idempotency and record the external operation ID. A network timeout may mean the external effect already happened: reconcile ambiguous outcomes instead of blindly creating another. If no external dedup/status API exists, mark the limitation and route ambiguous cases for review; do not promise exactly once.
6. **Retry deliberately.** Transient errors use bounded exponential backoff/jitter and respect relevant retry hints. Permanent validation/rights/auth errors become durable terminal failures. Bound attempts, total age, payload size, downstream concurrency and per-account expense. A 2xx response means the HTTP delivery can be removed; send it only after durable success or durable, tracked handoff. A failed operation can be acknowledged after its terminal failure is safely recorded.
7. **Treat long jobs as separate executions.** A Cloud Run handler may launch a Job and return promptly, but that only acknowledges launch. Persist execution mapping/status and reconcile launch ambiguity, retries and completion; duplicate launch must not duplicate effects. Use operation IDs throughout. Do not hold an HTTP delivery open beyond its supported deadline merely because a Job can run much longer.
8. **Own failure and replay.** Keep queryable failed operations independently of Tasks deletion or expiring DLQs. Alert on oldest unfinished age, repeated attempts and terminal failures; protect failure payloads. Replay through authorization with the same operation identity, a recorded reason and compatible payload version. Pause a broken consumer before replaying a poison backlog. Define retention/deletion by recovery/privacy policy; DLQ is not an archive or backup.

In a PostgreSQL-only queue, the job row itself can be the outbox/ledger; separate tables are not mandatory. A managed dispatch queue does not eliminate the database business record. Conversely, do not add an outbox for an operation that is already correctly synchronous and transactional.

| Tiny edge-native transform/R2 event | Edge event; compatible bounded runtime | Cloudflare Worker/Queues only where already useful | Workers CPU/subrequest limits apply. Not a conventional Go server or arbitrary long-running Python binary |
| Content drafting/TTS/transcoding/dataset preparation | Editorial action/release window | Owner Mac tools/agents; deterministic Content Factory validation | Device availability, power, supervision, usage caps and media rights remain real costs; not continuously available production compute |
| Repository validation/publication | Commit/manual or best-effort scheduled workflow | GitHub Actions under existing repository contracts | Bounded CI permissions/secrets; logs/artifacts with appropriate retention. Do not turn CI into a learner-facing job host |
| Production reconciliation/maintenance | Business schedule and explicit catch-up window | Cloud Scheduler → bounded Cloud Run handler/Job | Idempotent window key, retry policy, durable failed state; cloud owns availability rather than owner's Mac |
| Continuous high-volume consumer | Only after measured sustained utilization/latency requirement | Dedicated worker or appropriate Cloud Run worker-pool/instance-billing model | Entire lifecycle CPU/runtime may bill. Requires shutdown, leases, monitoring, backpressure and restart recovery; not a $0 default |
| Specialized AI inference/GPU | Only after actual model/latency/privacy need | Re-evaluate Modal/other existing AI profiles for exact workload | Credits, model loading, GPU RAM and external AI charges separate. No learner-runtime AI or GPU requirement is established here |

**Cloud Run lifecycle:** request-based billing allocates CPU during requests, not an unlimited background-compute entitlement after response. Untracked Go goroutines, Python threads, FastAPI `BackgroundTasks` and Next `after()` callbacks are not durable queues. FastAPI background tasks execute within the application lifecycle; process termination can lose them. Instance-based billing can allocate CPU outside requests, but instances can still terminate and the lifecycle bills. Jobs have their own execution/retry/timeout model. Choose durable dispatch or Jobs when completion matters; do not change billing mode merely to hide an untracked background thread.

### 14.7. Schedules and cron

Event-driven execution wins when a real event already identifies the operation. Do not install cron just to discover events the application already knows about. Scheduling creates a trigger, not an exact-time completion SLA.

| Candidate | Free class / cadence and timezone | Delivery, retry and missed-run behavior | Selection |
|---|---|---|---|
| **Cloud Scheduler** | `PERMANENT`; allowance and per-job meter in Google SSOT; minute-level cron, UTC default, IANA timezones | At-least-once; explicitly configure retry because defaults do not retry failed executions. | **Workers Cron** | Existing Workers Free allowance; minute-level UTC, bounded cron count/CPU; wall time is not CPU time | Config changes can take time to propagate. No sufficient documented durable catch-up/retry contract was established for this comparison | Runner-up for bounded edge-native maintenance, not a newly added bridge into Go. Application must own reconciliation if missed work matters |
| **GitHub Actions schedule** | Repository-plan CI entitlement; minimum five-minute cron; timezone configuration must follow current workflow syntax | Delays and dropped runs under load; inactive public repositories can have schedules disabled. Default-branch and repository operational dependencies | Repository/editorial maintenance only. Not the default production business scheduler |
| **QStash schedules** | Recurring Free allowance, bounded schedule count/delivery; minute cron, UTC default and IANA timezone option | HTTP delivery/retry/DLQ semantics and usage meters apply; short activation delay possible | Useful if QStash already wins dispatch. ### 14.8. Rate limiting and cost safety

| Problem | Smallest correct control | Failure behavior |
|---|---|---|
| Public traffic floods | Bounded local request/body/concurrency limits; existing Cloudflare WAF/rate rules where eligible | IP limits are coarse signals; tune for shared Vietnamese mobile/NAT networks. Cloudflare Free rate-rule availability is limited; do not assume enterprise bot protection |
| Login/recovery abuse | Existing auth controls + server-side account/IP-sensitive limits and enumeration-safe responses | Never trust browser counters; do not deny all learners behind one NAT. Sensitive endpoints need a defined degraded/deny policy |
| Per-account feature allowance | Atomic PostgreSQL reservation/consume keyed to internal learner identity and period | Strong authoritative decision across Go replicas; no allowance reset because a cache evicts or restarts |
| Paid AI/expensive processing | Durable allowance/budget reservation + operation ID before enqueue; queue dispatch/concurrency limits | Fail closed for unverified expensive work; reconcile failed/ambiguous external charges and reservations |
| Upload limits | Authorize object/account/content type; enforce actual size/format during verified finalization; bounded presigned capability | URL signing is not proof of file content or one-time use. Quarantine/reject excess; avoid media proxying solely for transfer |
| Provider bill safety | Provider quotas, finite retries/job deadlines, scale/concurrency and log limits; alerts plus documented spend-control limitations | Budget alerts are not invoice caps. Run caps do not cap egress, other services or already-running work; track gross meters separately |

Cloudflare protects only traffic that actually passes through it. A public `run.app` origin can bypass edge-only restrictions unless a verified origin-access design prevents it. Do not trust arbitrary forwarded IP/Cloudflare headers from the public internet. Adding a load balancer/Cloud Armor solely to complete a hypothetical Free architecture is not authorized or cost-neutral. Application-side account authorization and expense accounting remain necessary.

Local limits multiply across replicas and reset on restart. Upstash can improve shared approximate counters, but consistency, free inactivity, eviction and failure behavior must match the threat model. Workers KV's eventual consistency is unsuitable for strict distributed enforcement. Database transactions are appropriate for durable feature/paid quotas, but high-volume edge floods should not become a write per request against Neon. Apply layered controls with separate purposes rather than routing every problem through Redis.

### 14.11. Observability, exit and adversarial review

Use platform logs/metrics initially. Structured events include correlation ID, operation ID, payload/schema version, attempt, result/error category, duration and queue/execution identifier; avoid tokens, answer keys, full recordings or unnecessary learner identifiers. Track error/cold-start behavior and DB connections/active compute. When async is enabled, add oldest unfinished age, pending/running/failed counts, retries, terminal failures and missing completions. When cache is enabled, add hit/miss/fill latency, evictions/limit errors and source fallback load. Alert thresholds follow defined freshness/completion/recovery and budget objectives, not invented traffic baselines. Sample/retain logs deliberately; ingestion can bill even when compute is free.

| Dependency | Smallest boundary / provider-specific part | Migration and rollback |
|---|---|---|
| Cache | Only actual key/revision/freshness/invalidation needs; Redis/KV SDK can stay inside the integration that uses it | Disable reads, fall back to source with load limits, rebuild/warm selectively. Disposable cache requires no business-data export; authoritative values must never exist only there |
| Tasks / QStash / queue | Submit operation reference; observe durable status; authenticate delivery; process idempotently. Provider retry headers, JWT/OIDC and task names stay at delivery boundary | Pause new dispatch to old system, retain ledger, route new operations to new queue and drain/reconcile old deliveries. Overlap is safe only with effect deduplication. Queue export/DLQ is not universal or complete; recreate pending dispatch from ledger |
| Scheduler | Trigger one named authorized operation/window, not embed business logic in cron | Disable old trigger, change destination, preserve window dedup/catch-up; rollback destination without replaying completed effects. Account for already-dispatched invocations |
| Runtime / Python Job | OCI application/job plus explicit inputs, output references, retry/status contract; Jobs launch API is provider-specific | Keep compatible worker versions until backlog drained; migrate images/config and map execution IDs. Rolling back code does not undo completed external effects |
| Database / storage | Existing standard PostgreSQL migrations/export/restore and S3-compatible media access, with provider-specific IAM/presigning kept narrow | Tested data and object copy/restore, digest verification, controlled cutover; CDN purge/revisioning and auth identity invariants preserved. Backups are not verified merely because an export command exists |
| Logs | Structured application events and correlation IDs before vendor-specific tracing | Preserve necessary audit/operation records in the durable system; shorter-lived vendor logs are supplementary |

Do not create a universal cache/queue/scheduler interface framework. A small real integration boundary is sufficient. Shared Redis and per-provider SDK types must not become business identity, billing or learning-record semantics. Exporting a database or re-enqueuing pending operations is not automatic session/password/OAuth migration; §13's identity constraints still apply.

| Adversarial question | Finding / consequence |
|---|---|
| Can CDN eliminate Redis? | Often for public versioned content; assess actual remaining hot data, not total request count |
| Can HTTP cache eliminate application cache? | Yes for eligible responses; 304 alone may still execute SQL |
| Can SQL/indexes eliminate cache need? | Often; measure query plans before adding another network hop |
| Does Redis reduce Neon compute? | Not necessarily; active-time and other queries/writes remain |
| Does Redis worsen failures? | Yes if mandatory or fallback stampedes the DB; source must remain correct without it |
| Does PostgreSQL queue polling prevent sleep? | Frequent polling can; bounded/event-driven draining is conditional, not automatically free |
| Does Tasks cover the async need? | Yes for designated retryable HTTP tasks within its deadline; long jobs need tracked handoff |
| Do Queues add unnecessary boundaries? | For ordinary Go/Python tasks, usually; edge-local/R2-event work can justify them |
| Can work stay synchronous? | Prefer it if measured response/CPU budget and retry safety permit |
| Is the job editorial? | Mac + deterministic validation + CI publication is preferred |
| Is persistent worker required? | No evidence yet; require continuous-demand/latency evidence before paying for idle lifecycle |
| Is cron reliable enough? | Depends on completion window; best-effort repository schedules differ from business reconciliation |
| Are retries/idempotency correct? | Only after operation IDs, atomic effects, deadlines, ambiguity handling and recovery tests |
| Can duplicates create duplicate bills/history? | Yes without durable effect uniqueness/external idempotency; provider dedup windows are insufficient |
| Can backlog grow unbounded? | Apply admission, age/attempt limits and per-account budgets; queue quota exhaustion is visible failure, not success |
| Can rate limiting hurt shared-IP learners? | Yes; combine coarse IP protection with authenticated identity and explicit account policy |
| Can private responses leak? | Yes through cache-everything/key errors; bypass shared caching and test cross-account/cookie/RSC variants |
| Is rights withdrawal safe? | Stop new access and purge relevant CDN versions; browser/downloaded copies cannot be recalled |
| Does it work without Redis? | That is the selected default and the required fallback for any later disposable cache |
| Can providers be replaced? | Pending operations/authority must remain in portable durable records; delivery semantics, export and drain still require tests |
